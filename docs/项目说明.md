# Human-Agent 协作工程平台项目说明书

这是一份面向**第一次听说这个项目、不了解 AI Agent 或软件工程**的完整说明书。它不假设你读过规格、架构决策或 TypeScript 源码。读完你应能：

1. 用自己的话说明：它不是聊天机器人，也不是「再做一个 Copilot」。
2. 分清 **Project / Specification / Work Item / Execution / Agent / Kernel** 这几组最容易混的词。
3. 讲清楚一次「从需求到合进主分支」在平台里经过哪些关口、人要做什么、Agent 能做什么、机器保证什么。
4. 在本机启动系统，看懂首页、健康页和 OAuth Demo 跑出来的结果。

正式术语以仓库根目录 [`CONTEXT.md`](../CONTEXT.md) 为准。本文用中文讲解；英文专有名词（Human、Work Item、Execution 等）请原样使用，不要擅自换成「员工」「任务」「会话」这类日常词——那些词在本项目里含义不同，混用会把设计讲错。

# 第 0 章　先建立直觉

## 0.1 一个会乱掉的下午

假设产品要做「本机可演示的登录」：

- 小海是 **Owner**，对项目结果负责。
- 小陈是 **Member**，主要盯界面。
- 他们手头有三个会写代码的 Agent：一个是公司发布过的「后端正式工」、一个是小陈自己长期调教的「前端助手」、系统还根据缺口生成了一个「只做验收」的临时 Agent。

如果只用普通 Coding Agent 聊天窗口：

- 每个人开一个对话框，Agent 各自改同一份 `src/oauth.mjs`。
- 有人把接口改了，前端还按旧字段调。
- 某次生成失败了，没人分得清「需求没了」还是「这一次尝试没做成」。
- Git 能 merge 进主分支，但测试是红的——Git 看不出「语义冲突」。
- 事后问「当时依据哪一版需求、谁批准合进去的」，聊天记录给不出工程答案。

乱，不是因为 Agent 「不够聪明」，而是因为**缺少团队级的共享项目状态**：权威需求、授权边界、一次尝试与任务本身的分离、制品版本、可验证的合并。

## 0.2 这个平台补的是哪一层

可以把常见工具叠成三层：

```text
上层：人怎么商量、怎么授权、怎么验收、怎么留下历史
      ← 本平台主要做这一层

中层：Git 仓库、分支、diff、测试命令
      ← 本平台会用，但不替代 Git

下层：某个具体 Coding Agent（Pi、以后的其它内核）怎么「想」和调工具
      ← 本平台故意当成黑盒，不解析
```

所以：

- 它**不是**让你在网页里跟 GPT 闲聊写代码（第一阶段甚至**没有** Agent 群聊）。
- 它**不是**再实现一个 Git。代码仍在 Git 里；平台管的是「这次尝试用哪棵工作树、合进去前跑过哪些门禁」。
- 它**不是**保证生成代码正确。它保证的是：**没通过你们配置的验证，就不能进受保护的共享分支**；并且关键动作留得下账。

## 0.3 用一张图记住主链

```text
人把需求写成带稳定编号的 Specification，评审后变成 Effective（生效版）
        ↓
拆成 Work Item（正式工作条目），排成有依赖的图，人登记「我们线下同意这么拆」
        ↓
人把三类 Agent 请入本项目（Membership），再手动指定谁做哪条 Work Item
        ↓
每一次动手都是一次独立的 Execution：单独的 Git 工作副本，互不抢同一目录
        ↓
需要交接时发布带哈希的 Artifact；下游必须显式采用某一版，不能靠「群里说过」
        ↓
要合进主分支：排队、在最新基线上 rebase、跑 Verification，通过才叫 mergeable
```

后面每一章都在给这条链加细节。读的时候对照这张图，不容易迷路。

# 第 1 章　这个软件是什么、不是什么

## 1.1 正式名称与阶段

仓库名：`human-agent`。

产品定位：**Human-Agent Collaborative Software Engineering Platform**（人与 Agent 协作的软件工程平台）。

你现在看到的是**第一阶段**：证明两个人 + 三类 Agent，能围绕**同一个 Git 项目**，把「规范 → 工作 → 隔离执行 → 制品 → 干预/回溯 → 协调冲突 → 验证合并」**重复跑通**。完成标准不是「Agent 写出了酷代码」，而是这条闭环可复现。

运行方式：**本机原生**。Web、Server、Worker、PostgreSQL 都装在你电脑上。不用 Docker，不拆成一堆微服务，不引入 Redis/Kafka。

## 1.2 和你可能听过的产品差在哪

| 你熟悉的 | 它擅长 | 本平台额外坚持的 |
| --- | --- | --- |
| ChatGPT / 对话式 Coding Agent | 单人委派、快速出草稿 | 多人共享状态；任务与一次尝试分开；合入要验证 |
| GitHub + PR | 代码评审与合并 | 合并前的意图、合同版本、语义冲突、谁被授权执行 |
| Jira / 看板 | 票与状态 | 票必须挂到生效规范的稳定 ID；执行有隔离工作区 |
| CI（GitHub Actions 等） | 流水线测试 | 测试配置是项目里的 Verification Profile；和 merge 队列绑在一起 |

## 1.3 第一阶段刻意不做

把「不做」写清楚，是为了避免你按错误期待去找功能：

- 没有 Agent 群聊、没有「@所有人」的频道。协作载体是 Work Item、Artifact、Decision、Inbox。
- 没有企业登录、没有复杂角色矩阵。项目里人只有 **Owner** 和 **Member**。
- 不解析 Pi（或其它 Agent）脑子里的推理过程、工具循环、内部 session 树。
- 不自动给 Agent 打分、排序、推荐「雇哪个」。缺口只展示 **Capability Gap**，人选仍由人指定。
- 不把探索性改动直接送进受保护分支。
- 不声称外部副作用（已 push、已部署、已写第三方库）能一键撤销。平台里的「回溯」主要指：**从检查点开一条新的执行路径**，旧路径还在。

## 1.4 你电脑上会看到几个程序

启动 `pnpm dev` 之后，至少有四样东西在工作：

1. **浏览器里的 Web**（默认 http://127.0.0.1:5173）：给人看的界面。
2. **Server**（默认 http://127.0.0.1:3001）：接收「命令」、查询、推送更新。
3. **Worker**：后台工人。真正去跑一次 Execution、调 Agent、跑测试命令。
4. **PostgreSQL**：权威账本。项目状态、事件、任务队列、Worker 心跳都在这里。

Git 仓库在磁盘上另有一份（你的项目代码）。每次 Execution 还会在旁边长出隔离的 **worktree**（工作树），避免两个 Agent 同时改同一个文件夹。

若 Server 日志里有 `Command API enabled.`，说明「创建项目」这类写入已经接通数据库。只有健康检查、创建失败，多半是旧进程没重启，或 `.env` 里没有 `DATABASE_URL`。

## 1.5 当前版本已经做到哪里（2026-08-29）

先说结论：**第一阶段需要的后台协作闭环和可重复 OAuth Demo 已经跑通；Web 已经能查看这条闭环产生的主要项目记录，但还不是所有操作都有可视化表单。**

当前已经实现：

- 本地创建 Project、导入 Git 基线并设置受保护分支与 Verification Profile；
- Specification 的创建、评审、生效、换版和稳定条款 ID；
- Work Item、Work Graph、Coverage 和线下共识结果登记；
- 两名 Human 与三种 Agent 来源的项目 Membership、能力检查和人工指派；
- Mock 和 Pi 两种 Executor Adapter，其中 Mock 用于稳定测试，Pi 用于真实 Agent 执行；
- 每次 Execution 的独立 Git worktree、状态、失败恢复、Human Intervention、Checkpoint 和分支；
- Artifact、Decision、Context Package、依赖过期传播和 Inbox；
- Change Intent、Contract Ownership、冲突分类、merge queue、Verification 和受保护合并；
- Web 项目列表、项目总览、规范/工作、团队、执行、制品、决策、待办、合并与完整 Timeline；
- 一键 OAuth 协作 Demo：可重复创建新项目并自动跑完正常执行、一次失败恢复、合同变更和三个验证合并。

当前还没有或不属于第一阶段：

- 没有为每一种 Command 都做 Web 操作表单；完整能力目前主要由应用层 Command API 承载，一键 Demo 负责展示纵向闭环；
- 没有生产级登录与身份认证网关。Command 中虽然有 Human/Agent actor，当前服务仍是在本地可信环境里使用这些身份信息；
- OAuth 是 Demo 所开发的业务功能，**不表示平台自身已经用 OAuth 登录**；
- 没有 Agent 市场、Digital Employee 自动推荐或自动排名。Digital Employee 和 Private Agent 由 Human 手动选，系统只报告能力缺口；
- 没有云多租户、企业 SSO、生产部署控制和完整 RBAC；
- 不自动解决高风险合同或语义冲突，也不保证所有外部副作用都可撤销；
- Pi Adapter 已接入统一契约，但要真实调用 Pi，仍需本机安装 Pi 并配置相应凭证。默认验收不依赖它。

因此，看当前产品时应把它理解成：**一个已经验证核心工程模型的本地平台原型，而不是已上线的企业 SaaS。**

第一阶段的 42 条本地验收工单均已标记为 `resolved`。本文更新时，自动化测试结果为 **60 项通过、4 项跳过**；跳过的是需要真实 Pi 环境的可选直播契约，不影响 Mock 驱动的可重复平台验收。

# 第 2 章　五对最容易混的词（必读）

后面所有章节都建立在这五对区分上。建议读完本章再往下。

## 2.1 Work Item ≠ Execution

**Work Item** 是「这件事需要被做成」：来自生效规范，带着目标、验收条款、风险、所需能力。它是项目待办，可以改派、可以等依赖、可以因规范变更而过期（`stale_spec`）。

**Execution** 是「某一次具体动手」：某个 Agent（或人）在某套固定配置下试了一次。它可以失败、超时、被取消、状态未知。

错误想法：「Agent 崩了，所以这条需求失败了。」  
正确想法：「这一次 Execution 失败了；Work Item 还在，可以再开一次 Execution，或换人做。」

类比：乐谱是 Work Item；某一场演出是 Execution。演出砸了，乐谱不必撕掉。

## 2.2 Agent Actor ≠ Kernel（Executor）

**Agent Actor** 是项目里的「谁」：数字雇员、私人 Agent、系统生成 Agent。它有来源、赞助人、权限、信任状态。

**Kernel / Executor** 是「用哪台引擎跑」：第一阶段默认真实引擎是本机 **Pi** CLI；测试和 Demo 用 **Mock**（按剧本成功/失败，不调用真模型）。

错误想法：「我们雇了 GPT-4。」  
正确想法：「项目里有一个 Digital Employee Membership，这次 Execution 选用 Pi 作为 Kernel。」同一个 Agent 将来可以换 Kernel（只要 Adapter 接上）；Kernel 换了，并不自动等于换了一个项目成员。

## 2.3 Specification ≠ Prompt

**Prompt** 是某次对话里的一句话，易变、难追溯。

**Specification** 是版本化的项目意图：Markdown 正文进 Git，平台抽出 **稳定 ID**（如 `REQ-AUTH`、`AC-TOKEN`）。只有走到 **effective** 的版本才是正式工作的权威来源。改生效稿必须出**新版本**，不能在原文上偷改。

错误想法：「我在聊天里说了要支持刷新令牌，就算需求了。」  
正确想法：「刷新令牌要成为某条 AC 的正文，经过评审变成 effective，Work Item 引用那个 AC ID。」

## 2.4 Checkpoint ≠ 撤销 / Ctrl+Z

**Checkpoint** 是在一个**稳定边界**上，同时钉住：

- 工作区代码快照（Git commit），以及
- Kernel 给的一串**不透明**引用（平台看不懂里面是什么，只负责原样还给 Adapter）

然后你可以 **fork** 出一条新的 Execution（新分支）。**旧的那次执行还在**，供对比和审计。

错误想法：「回溯就是把主分支和时间倒回去。」  
正确想法：「回溯是开新尝试；共享历史上已经 push / 部署的东西，平台不会假装没发生过。」

若 Kernel **不能**精确恢复内部状态，平台只能从代码快照新开会话，这条分支必须叫做 **reconstructed**（重建的），不能对外宣传成「精确回到当时的 Agent 脑子」。

## 2.5 可追溯 ≠ 可撤销

平台把重要操作记成带因果的事件（谁、对什么、结果、关联哪次命令）。你可以事后画出时间线。

这**不表示**能撤销一次已经发生的对外付款、一次 `git push`、一次生产部署。那些需要另外的补偿流程。教材后文提到「历史只追加、禁止改旧账」，指的是**账本不能偷改**，不是「宇宙倒带」。

# 第 3 章　剧组：人和三类 Agent

## 3.1 Human

**Human** 就是真人。可以创建项目、邀请同事、评审规范、指派工作、批准权限、登记线下共识、在执行中途干预。

第一阶段项目内角色只有两个：

- **Owner**：能做导入仓库、邀请成员、采用正式雇员、处理高风险所有权等「项目级」动作。
- **Member**：参与工作，但不能冒充 Owner 做那些动作。

没有「管理员偷偷改历史」的设计。人在平台里做的关键事都会留下 Traceable Operation。

## 3.2 为什么 Agent 要分成三类

因为来源和信任不一样，不能都叫「机器人」：

### Digital Employee（数字雇员）

- 像「公司发布过的正式工种」：有 **Release**（不可变版本），有 provenance（从哪来的）、内容哈希、声明的能力。
- 项目采用时**钉死某一个 Release**。发布方以后出 1.1，不会悄悄替换你正在用的 1.0。要升级必须走显式操作（第一阶段以「再导入/再采用」的纪律为主）。
- 适合：后端 OAuth 这种希望「可复用、可审计来源」的能力。

### Private Agent（私人 Agent）

- 像「同事自己长期养成的助手」，不是公司正式编制。
- 带入项目时要交可审查的 **Manifest、配置摘要、权限需求、内容哈希**。平台做一份**项目内副本**，以免这个人回家后又改了私人配置，影响正在跑的 Execution。
- **不读取**其私人聊天记忆。项目权威上下文另算（第 9 章 Context Package）。
- 适合：前端同学带着自己的 UI Agent 进组。

### System-Generated Agent（系统生成 Agent）

- 当现有人和 Membership **盖不住**某条 Work Item 声明的 required capabilities 时，平台只报告 **Capability Gap**（缺口事实），**不推荐**「雇 A 比雇 B 好」。
- 人可以批准系统生成一个 **Candidate**。在 qualification 或受限试用之前，它还不是可指派的正式成员。
- 适合：临时补一个「只做 QA」的角色，且必须有人点头。

三类都通过统一的 **Agent Membership** 进入项目，所以后面的 Work Item、Execution、权限协议可以共用；但来源、信任、准入门槛不同。

## 3.3 几个容易混淆的「人的角色」（与项目 Owner 不同）

这些词描述的是**对某个 Agent 的责任**，不是 GitHub org 的职位：

- **Creator**：最先做出这个 Agent 的人。创造 ≠ 在本项目说了算。
- **Cultivator**：长期调教指令、技能、风格的人。
- **Custodian**：跨项目保管 Digital Employee 版本与可移植性的人。
- **Publisher**：有权发布新 Release 的人/组织。
- **Project Sponsor**：在**本项目**为该 Agent 的角色和权限负责的人。

教材里记住一句即可：**把 Agent 做出来，和在本项目授权它改代码，是两件事。**

## 3.4 权限怎么算

有效权限取三者**交集**（最小权限）：

1. Agent 自己声明需要的；
2. 本项目 Policy 允许的上限；
3. Membership 里批准的。

临时多要一点：走 **Permission Request**（动作、范围、理由、期限），人批准或拒绝。

有些底线**不能**用普通 override 绕过：例如受保护分支、密钥、不可篡改的历史、宿主敏感路径。教材把它们理解成「建筑规范」：不是项目组投票能取消的。

## 3.5 指派工作

人**手动**选择哪个 Membership 做哪条 Work Item。平台会挡明显不合法的指派（例如能力对不上、还是 candidate 身份）。高风险强行指派必须留下理由和范围。

Agent 可以提出 **Assignment Concern**（能力不够、上下文缺、范围冲突），但**不能自己改派**。改派会生成新版本，旧指派记录还在。

# 第 4 章　需求怎样变成可执行的工作

继续 OAuth 例子。

## 4.1 先有 Git 项目，才有「工程基线」

Owner 创建 Project 后，导入一个**已经存在**的本地 Git 仓库，并指定：

- **base branch**：执行从哪份提交长出来；
- **protected branch**：最终允许合入的共享分支（常和 base 相同，例如都是 `main`）；
- **Verification Profile**：合入前要跑哪些命令（构建、测试等）。第一阶段 Demo 里常用一条永远成功的 `true`，用来证明「门禁被执行了」；真实项目应换成你们真正的测试。

导入过程是校验，**不会**把你工作区里未提交的脏文件清掉，也不会偷偷改你的共享分支。

## 4.2 Specification 长什么样

正文是 Markdown。平台认这种标题（不要改成别的格式，否则解析失败）：

```markdown
## REQ-AUTH Authorization
### AC-AUTHORIZE Local provider issues a one-time authorization code
### AC-TOKEN Token endpoint exchanges the code for an access token

## REQ-UI Login surface
### AC-LOGIN Login form is rendered by the local provider
```

要点：

- `REQ-…` 和 `AC-…` 是**身份**，不是第几行。你以后把段落挪位置，ID 不变，追踪才不会断。
- 每个 AC 必须写在某个 REQ 下面。
- ID 不能重复。
- 至少要有一条 REQ 和一条 AC。

平台把解析结果存进 PostgreSQL，正文仍以 Git commit/hash 关联，便于 diff。

## 4.3 Specification 的生命

```text
draft（草稿）
  → in_review（评审中）
  → effective（生效，正式工作只认这个）
  → superseded（被新版本取代）或 withdrawn（撤回）
```

非法跳转会被拒绝（例如生效稿直接改回草稿）。两人同时评审时，用 **expected version**（期望版本号）：你的屏幕还是旧版本，提交会被冲突拒绝，而不是悄悄覆盖别人的结果。

**生效稿不能原地修改。** 需求变了：出新版本（supersede）。引用了「已改变条款」的正式 Work Item 会进入 **`stale_spec`**，人必须选择暂停、重新规划或确认不受影响——不能假装没看见。

## 4.4 Work Item 与 Coverage

正式 Work Item 必须挂在 **effective** 规范上，并且验收条款 ID 必须真的存在。字段包括：目标、验收条款、风险、影响范围、所需能力等。

**Coverage Matrix** 回答：「这条 AC 现在处于哪一档？」

- `uncovered` 还没人认领  
- `planned` 已有工作条目  
- `implemented` 执行侧做出了东西（仍未必通过项目验证）  
- `verified` 通过 Verification 并完成合并等门禁后的状态  
- `waived` 人声明放弃并留下理由与登记者  

OAuth Demo 里典型拆法：

| Work Item | 覆盖的 AC | 需要的能力 |
| --- | --- | --- |
| 实现授权与换票 | AC-AUTHORIZE, AC-TOKEN | oauth.backend |
| 做登录界面 | AC-LOGIN | oauth.frontend |
| 做端到端验收 | AC-TOKEN, AC-LOGIN | oauth.qa |

它们可以连成图：例如前端和 QA **依赖**后端先完成（有向无环图；出现环会被拒绝）。

**Planning** 可以提出这张图，但**不能自己批准**。人在白板/会议里商量完，到平台上做 **Recorded Consensus**：记下结果、理由、登记人，并带免责声明——平台**没有**听到会议上每个人是否真的同意。

## 4.5 Exploration Work Item

有时你还不知道规范该怎么写，需要先探路。可以建 **Exploration Work Item**（有目标、边界、预期证据），**不必伪造**已经确定的 AC。

探路结果**不能**直接当成「已验证的共享产品」。要进主产品，仍须后续正式 Specification + 正式 Work Item + 验证。这是防止「周末实验变成默认行为」的闸门。

# 第 5 章　Agent 怎样被允许碰代码

## 5.1 入项三条路（对照 Demo）

OAuth Demo 会自动做完类似步骤，便于你对照界面上的 Team：

1. 导入 Digital Employee **Release 1.0.0**（能力 `oauth.backend`）→ 项目 **Adopt**。  
2. Member 提交 Private Agent（能力 `oauth.frontend`）→ 生成项目内副本 + Membership。  
3. 发现 QA 能力缺口 → **GenerateSystemAgent** → 人 **Qualify** 后才能指派。

Team 视图应能看出：来源类型、名称、信任状态（candidate / trial / qualified 等）。

## 5.2 为什么没有「智能推荐雇谁」

推荐算法会把责任藏进黑盒：为什么派这个 Agent？分数怎么来的？出了问题怪谁？

本平台只做**硬约束**（能力、信任、权限交不交得上）和 **Gap 展示**。人选是团队线下共识，再手动指派。这是设计，不是功能没做完。

## 5.3 Context Package：Agent 开工时到底「知道」什么

每次 Execution 启动时，平台打一份**当时的**上下文包裹，之后项目再变，**这一次尝试不会被静默换成新包裹**。里面是项目事实，例如：

- 这条 Work Item 是哪条；
- 当时生效的 Specification 版本；
- 已正式采用的 Artifact 版本（不是「群里提过的草稿」）；
- 已登记的 Decision；
- 基线 commit；
- 权限。

明确**不包含**：密钥（密钥走运行时注入）、私人记忆、未采用的历史、draft 制品。

这样比较两次 Execution 才公平：输入版本是钉死的。

# 第 6 章　一次 Execution 在机器上发生了什么

## 6.1 从点「开始」到 Worker

人（或 Demo 脚本）发出 **StartExecution**：

1. 检查 Work Item 不是 `stale_spec`，探索项不能借此直接「验收通过共享产品」。  
2. 若项目已绑 Git：在仓库旁创建独立目录，分支名形如 `ha/execution/<执行ID>`，基线是项目记录的 baseline commit。  
3. 写入一条 **job**（待办任务）。  
4. Execution 先处于 `queued`。

**Worker** 定期心跳（证明自己还活着），并从 PostgreSQL 领取 job（有租约 lease，避免两个人同时跑同一条）。然后调用选定的 Executor：`start` → 状态进入 `starting` / `running`，再到终态。

## 6.2 Execution 状态（你会在界面上看到）

```text
queued → starting → running
       → waiting_for_human（等你说话或批准）
       → paused
       → completed / failed / cancelled
       → unknown（引擎状态无法确认）
```

**unknown 是一等公民。** Worker 崩溃、Pi 没响应、进程被杀，平台**不许瞎猜**已经成功或已经安全取消。此时应：保留工作区、通知 Inbox、等人决定重连、分支或取消。**禁止**为了「看起来干净」自动删掉别人的 worktree。

## 6.3 为什么必须隔离工作区

两个 Agent 同时改同一个文件夹，会互相覆盖、无法解释 diff 是谁的。平台为每次 Execution 准备：

- 自己的 worktree；
- 自己的分支名；
- 固定的 base commit。

内核**不能**自己改去碰宿主敏感路径或擅自切换主分支。代码事实以平台读取的 Git 状态 / diff 为准，而不是 Agent 在对话里「我已经改好了」。

## 6.4 Mock 和 Pi

**Mock Executor** 按 `scenario` 演戏：

- `success`：在工作区写下简单产物并完成；  
- `failure` / `timeout`：失败（超时仍是失败，不是成功）；  
- `pause`：停在等待人；  
- `unknown`：无法确认。

适合测试和 Demo。OAuth Demo 走 Mock，这样没有模型 API Key 也能把闭环跑完。

**Pi** 是第一阶段默认**真实**内核：在受控目录里调本机 `pi` 命令。平台把 `--session` / `--fork` 之类当成不透明字符串，不打开 Pi 的内部文件当业务逻辑。没配凭证时，真实任务可能变成 `unknown`——这是诚实行为。

测契约时：Mock 总会跑；Pi 直播测试需要环境变量 `PI_LIVE=1`。实现上，契约测试套件不放在 SDK 主入口，以免 Worker 启动时误加载测试框架 Vitest（那是曾经真实出现过的故障）。

## 6.5 平台如何判断「做完了」

Agent 说完成不算。平台会：

- 自己看 Git 是否有变更、diff 是什么；  
- 按项目 **Verification Profile** 跑命令，记下命令、输出、是否通过、耗时。

只有验证通过且满足所引用 AC 的路径，才能把 Coverage 往 `verified` 推，并允许进入合并候选。无变更、脏工作区、验证失败，都是一等路径，要能在测试里稳定复现。

# 第 7 章　人如何介入；失败后如何分叉

## 7.1 Intervention（干预）

对运行中的 Execution，人可以发结构化动作，而不是在聊天里喊「停一下」：

- 发送补充输入  
- 暂停 / 恢复  
- 中断  
- 取消  

界面应只展示**当前 Kernel 声明支持**且**当前状态允许**的动作。非法或打到一半状态的操作会明确失败。重试同一命令靠幂等键，避免副作用执行两次。

## 7.2 复合 Checkpoint

在稳定边界（例如已暂停）请求 Checkpoint。成功则**同时**得到：

- Workspace 的 commit；  
- Kernel 的 opaque 引用；  
- 当时的项目版本与输入版本。

任一侧失败：**不发布**「可恢复检查点」，但留下失败证据。禁止用「差不多同一时间」的两样东西拼成假检查点。

## 7.3 Exact 与 Reconstructed

从已发布 Checkpoint **Fork**：

- Kernel 支持 fork：新 Execution 为 **exact**，工作区与内核引用应对齐到同一节点。旧 Execution 不变。  
- Kernel 不支持：只能 **reconstructed**，必须在 UI 和事件里永远标明「不是精确回溯」。  
- 任一 restore 失败：新分支不得进入 running，原 Execution 不受牵连。

同一 Work Item 上可以有多条探索分支，但**同时最多一个 selected candidate** 能往共享状态推进（进 merge 队列）。换选是新操作，历史保留。

## 7.4 失败页应让人看见什么

事实、影响范围、最近可用恢复点，以及：重试（新的 Execution）、加预算、从检查点分支、取消。平台**不会无限自动重试**；每次重试都是可区分的尝试。

# 第 8 章　并行修改如何不在最后一天爆炸

## 8.1 Change Intent（变更意图）

开工前登记「我可能动哪些文件、符号、合同」。它有自己的生命周期，和 Work Item、Execution 分开——预测错了可以出新版本，不必假装没说过。

范围重叠默认是**软预约**：警告双方，**不永久锁文件**（否则并行能力为零）。高爆炸半径的路径（API 合同、Schema、共享类型、依赖版本）可以设 **Ownership**：不满足规则就拦住，或要求人的显式 override。

## 8.2 四种冲突

| 种类 | 直观理解 | 典型处理 |
| --- | --- | --- |
| **text** | 同一文件同一段文字对不上，Git rebase/merge 冲突 | 人在隔离区解决文本 |
| **symbol** | 函数/类型同名不同含义 | 需要设计层对齐 |
| **contract** | 接口/协议版本不兼容 | 失效传播 + 显式采用新版，禁止模型「猜着改」 |
| **semantic** | Git 很干净，但测试/构建红了 | 记 Semantic Conflict，不能标成普通文本冲突 |

**Semantic** 是本平台相对「只会 Git」的产品的关键差别：干净的 merge 仍可能是错误的产品。

## 8.3 Merge Queue

流程概要：

1. 人把某次 Execution 标为 **selected**。  
2. 创建 **Merge Candidate** 进入队列（有确定顺序）。  
3. 在隔离环境相对**当前最新基线** rebase（前面的人刚合进去，你必须站在新基线上再验证）。  
4. 跑 Verification Profile。  
5. 通过 → `mergeable` → 才允许合入 **protected branch**。  
6. 失败 → conflicted 或 validation_failed；低风险可有限自动修，高风险/超次数 → Inbox 升级给人。

共享分支在验证完成前**不应**被改掉。未选中的探索分支保持可看，但不能私自推进共享状态。

合入成功后，相关 Change Intent 应释放；Work Item 的 coverage 可以走到 verified。

# 第 9 章　制品、决策、收件箱、时间线

## 9.1 Artifact（制品）

协作应通过「带哈希的版本化产物」，而不是「我在聊天里贴了一段 JSON」。

- 状态：`draft → published → superseded | deprecated`  
- Consumer **只能采用 published 的某一版**，采用记录挂到 Consumer 的 Work Item 和操作者。  
- 新版本可以取代旧版，但**不会悄悄改写**已经发生的采用记录；旧消费者会被标 stale，需要显式改用新版。

OAuth 例子里，后端发布 `contract/oauth.json` 的 v1，前端必须 adopt v1；若后端发布 v2 并 supersede，前端工作会过期，直到采用 v2 并改适配。

## 9.2 Decision 与 Recorded Consensus

Agent 可以提交 **Decision Proposal**（问题、选项、证据、影响），不能自己标成已决定。

人登记决定时写下结果、理由、登记者。登记者**不是**平台验证过的「唯一决策者」——可能只是会议纪要的执笔人。以后要改结论，用 **superseding Decision**，禁止编辑旧行。

这与第 4 章的 Recorded Consensus 同一哲学：**平台保存结果，不伪造讨论过程。**

## 9.3 Inbox

Inbox 不是事件消防水管。只放**现在需要人动手**的：缺口、权限申请、失败、预算、unknown、stale、冲突、合并就绪等。处理完或被取代的离开待办，历史仍能在时间线找到。普通浏览页面不会每点一次就记一条审计。

## 9.4 Timeline 与三类事件

- **domain**：权威业务事实（项目创建、规范生效、已合并……）  
- **telemetry**：执行过程观测（状态变化），不能当成「需求本身」  
- **audit**：安全相关操作  

每条领域事件有项目内序号 `project_sequence`，以及 causation / correlation，用来把「这条命令引起了后面哪些事」串起来。界面可用 SSE 按序号推送；断线用 cursor 只补漏，重复序号应忽略。

## 9.5 当前 Web 能查看什么

Web 不是只显示几个汇总数字。进入一个 Project 后，可以从不同视角查看同一批工程事实：

- **Overview**：项目基线、受保护分支、当前 Specification 和整体数量；
- **Spec / Work**：规范版本、需求与验收条款、Work Item、依赖和 Coverage；
- **Team**：Human Membership、Agent Membership、Agent 来源、能力、赞助人和信任状态；
- **Execution**：每一次尝试的 Kernel、状态、基线、Context Package、Verification 与失败信息；
- **Artifacts**：合同等制品的版本、内容、发布者、采用者和取代关系；
- **Decisions**：提案、最终登记结果、理由和记录人；
- **Inbox**：当前仍需要 Human 处理的事项；
- **Merge**：Merge Candidate、队列状态、Verification 结果和冲突；
- **Timeline**：按项目序号查看完整领域事件与执行观测事件。

列表中的记录可以点开详情抽屉，查看 ID、状态、版本、关联对象、权限、上下文、验证结果和原始事件数据。这样即使暂时没有对应的编辑表单，平台已经保存的关键信息也不会只能去数据库或终端里找。

需要注意：Web 的「可查看」比「可操作」覆盖更完整。当前最适合的体验方式是先跑一键 Demo，再沿着这些页面逐条检查结果。

# 第 10 章　实现结构（给要读代码的人）

## 10.1 一句话架构

**模块化单体**：一个 TypeScript monorepo，三个进程（Web / Server / Worker）共用同一套领域与数据库，而不是一堆微服务。

写入遵守 **ADR-0001**：每一次成功的业务变更，**PostgreSQL 同一事务**里写：当前状态表 + 不可变 Domain Event + Outbox。失败则三者都不留下。禁止「状态写进去了、事件没写」。

内核遵守 **ADR-0002**：Pi 等是黑盒；精确回溯靠「工作区快照 + 不透明内核引用」绑在同一边界。

## 10.2 仓库地图

```text
apps/web          界面（React）。开发时 Vite 把 /health /commands /projects 转到 3001
apps/server       HTTP。Hono。命令、查询、SSE、健康、OAuth Demo
apps/worker       无 HTTP。心跳 + processJob

packages/domain           状态机、错误类型、ID
packages/application      createPlatform()：所有 Command 的业务编排
packages/persistence      连接库、migration、事务提交、幂等表
packages/executor-sdk     Agent 引擎接口（契约测试在子路径 contract-suite）
packages/mock-adapter     Mock 引擎
packages/pi-adapter       Pi CLI 适配
packages/workspace-git    worktree / rebase / 合入受保护分支 / 测试用临时仓库
packages/verification     按 Profile 跑命令
packages/shared-contracts 跨端的小契约（如健康检查 JSON）
```

改需求语义：先想 Command 和状态机，再改 UI。不要在 React 里直接「发明」一种 Work Item 状态。

## 10.3 Command 是什么

所有改权威状态的动作都是一封 **Command 信封**，典型字段：

- `type`：如 `CreateProject`、`StartExecution`  
- `payload`：这次动作的数据  
- `actor`：谁发起（人 / Agent / 系统）  
- `idempotencyKey`：同样的键点两次 = 同一次，不建两个项目  
- `correlationId` / `causationId`：把一次用户操作和后续事件串起来  
- `expectedVersion`：我以为聚合体是第几版；不对就 409，避免静默覆盖  

HTTP 上就是 `POST /commands`。OAuth Demo 则是服务端按固定剧本连续发很多封 Command。

## 10.4 主要 HTTP

| 方法 | 路径 | 人话 |
| --- | --- | --- |
| GET | `/health` | 三个部件是否活着，挂了告诉你下一条命令 |
| POST | `/commands` | 写入 |
| POST | `/demos/oauth` | 一键跑教材里的 OAuth 故事（Mock） |
| GET | `/projects` | 列表 |
| GET | `/projects/:id` | 摘要 + 最近事件 + 健康 |
| GET | `/projects/:id/events?cursor=` | 实时推送 |
| GET | `/projects/:id/work` | 规范、工作条目、覆盖率 |
| GET | `/projects/:id/team` | 人与 Agent |
| GET | `/projects/:id/executions` | 各次尝试 |
| GET | `/projects/:id/artifacts` | 制品 |
| GET | `/projects/:id/inbox` | 待办 |
| GET | `/projects/:id/merge` | 合并队列与冲突 |
| GET | `/projects/:id/timeline` | 按层过滤的历史 |
| GET | `/projects/:id/decisions` | 决策 |

数据库未接通时，`/commands` 与 `/projects` 返回 JSON 503（不要再返回纯文本 `404 Not Found`——浏览器会把它误解析成数字 404）。

## 10.5 Command 目录（备查）

| 类型 | 人话 |
| --- | --- |
| CreateHuman / CreateProject | 登记人；建项目（创建时 expectedVersion 必须为 0） |
| ImportGitRepository | 挂仓库与验证配置 |

| CreateWorkItem / CreateExplorationWorkItem | 正式 / 探索工作 |

| AssignWorkItem / RaiseAssignmentConcern / ReassignWorkItem | 指派 |

| StartExecution / Intervene / CreateCheckpoint / ForkExecution / SelectCandidate | 执行与分叉 |

| RegisterChangeIntent / SetContractOwnership | 变更意图与所有权 |

## 10.6 状态机（备查）

```text
Specification:  draft → in_review → effective → superseded | withdrawn
Work Item:      draft → ready → assigned → in_progress
                → waiting_for_human | blocked | ready_for_review
                → completed | cancelled | stale_spec
                （注意：没有 failed）
Execution:      queued → starting → running
                → waiting_for_human | paused
                → completed | failed | cancelled | unknown
Artifact:       draft → published → superseded | deprecated
Decision:       proposed → decided → superseded | withdrawn
Change Intent:  proposed → reserved → active → released | superseded | conflicted
Merge:          queued → rebasing → validating → mergeable → merged
                旁路：conflicted | validation_failed | cancelled | stale
```

# 第 11 章　动手课

本章按「第一次打开电脑」写。命令在仓库根目录执行。

## 11.1 你需要事先安装的

- **Node.js 22 或更高**  
- **pnpm 9**（可用 `corepack enable`）  
- **Git**（2.28+ 更好，因为 `git init -b`）  
- **PostgreSQL 16**，装在本机，不要用 Docker  
- 可选：**Pi** CLI（真要跑真实内核时）

macOS 上 PostgreSQL 常用：

```bash
brew install postgresql@16
brew services start postgresql@16
echo 'export PATH="$(brew --prefix postgresql@16)/bin:$PATH"' >> ~/.zshrc
```

新开一个终端，确认 `psql --version` 看得到 16。

## 11.2 安装与启动

```bash
corepack enable
pnpm install
cp .env.example .env
pnpm check-env
pnpm db:init
pnpm dev
```

含义：

- `check-env`：缺什么会用中文告诉你下一条命令。  
- `db:init`：创建数据库并跑 migration。  
- `dev`：同时拉起 Web、Server、Worker。

打开 http://127.0.0.1:5173 。

环境变量（`.env.example`）：`DATABASE_URL`、`TEST_DATABASE_URL`、`HOST`、`SERVER_PORT`、`WORKER_ID`、心跳间隔、Worker 过期阈值。测试命令 `pnpm check` 需要真实 PostgreSQL 和这份 `.env`。

**改了 Server/Worker 代码必须重启 `pnpm dev`。** 只刷新浏览器不够。历史上出现过：健康检查是新的，创建项目仍打到只实现了 `/health` 的旧进程。

## 11.3 第一次建议怎么点

1. 看健康（侧栏 Health 或启动页相关提示）：Server、Worker、PostgreSQL 应「可用」。Worker 不可用时按提示启动 Worker。  
2. 点 **OAuth 协作 Demo**（不要先纠结自己填规范）。等待结束后应出现一个新 Project，摘要里有完成的 Work Item、合并数、处理过的冲突等。  
3. 打开 **Dashboard**：这是项目中心，不是聊天记录。  
4. **Spec / Work**：看生效规范和 Coverage。  
5. **Team**：两个人、三种来源的 Agent。  
6. **Execution**：多次尝试、kernel、分支类型。  
7. **Artifacts / Inbox / Merge / Timeline**：制品、待办、队列、按序号排列的历史。

自己点「创建 Project」也可以，那只建一个空壳，还要自行导入 Git、写规范——Demo 是为了先看见完整故事。

## 11.4 质量命令（给开发者）

```bash
pnpm check      # 类型检查 + lint + 测试
pnpm typecheck
pnpm lint
pnpm test
```

测试原则（读代码时也适用）：只断言**外面能看见的行为**和数据库里的事实，不断言 Agent「心里想什么」、也不断言函数调用次序。Git 相关测试用临时 fixture 仓库，用完删除。

## 11.5 Demo 实际自动做了什么（对照第 0 章故事）

脚本会：建项目、导入临时 Git（内含本地 OAuth 小模块和合同文件）、邀请第二个人、创建并生效规范、拆三条 Work Item 并连依赖、导入三类 Agent、登记共识、指派、跑 Mock 执行、发布/采用合同、处理重叠与过期、排队验证并合并。它**不登录**任何互联网 OAuth 提供商。

# 第 12 章　常见误解（FAQ）

**Q：这就是一个网页版 Cursor / Copilot 吗？**  
A：不是。那些产品优化「一个人把活交给模型」。本平台优化「人和多种 Agent 在同一工程基线上如何授权、验收、分叉、合并」。

**Q：为什么没有聊天？**  
A：第一阶段把聊天视为噪声源。正式协作走结构化对象。诊断时可以看可选的内核原始日志，但不作为领域逻辑。

**Q：Agent 失败了，需求是不是没了？**  
A：不是。失败的是 Execution。见第 2.1 节。

**Q：为什么系统不给我推荐最好的 Agent？**  
A：避免不透明排名。见第 5.2 节。

**Q：Git 都 merge 了为什么还报冲突？**  
A：可能是 Semantic Conflict：版本库干净，验证红了。见第 8.2 节。

**Q：回溯会不会把已经上线的功能撤回？**  
A：不会装成没发生过。回溯是新 Execution。见第 2.4–2.5 节。

**Q：Pi 和 Mock 哪个才是「真的」？**  
A：对工程闭环，Mock 可以是真的（可重复）。对「模型真的改了业务代码」，需要 Pi 且凭证可用。Demo 默认 Mock。

**Q：我想加第四种 Agent 或另一种模型。**  
A：实现 `AgentExecutor` Adapter，声明能力；不要把上层写成「解析某家 session JSON」。见 ADR-0002。

**Q：文档里的英文词能不能全部译成中文界面用语？**  
A：界面可以中文；**讨论设计时请保留英文专名**，否则和 `CONTEXT.md`、代码、工单对不上。

# 附录 C　你应能向别人复述的三段话

**这段话说明它是什么：**  
这是一个以 Project 为中心的协作层。人和三类 Agent 共用同一份生效规范和同一 Git 基线；每一次动手都是隔离的 Execution；合进受保护分支前必须通过项目自己的验证配置。

**这段话说明它保证什么、不保证什么：**  
它保证账一致（状态和事件同一事务）、尝试可隔离、失败可分叉、并行冲突可分类、未验证不能进共享分支。它不保证生成代码正确，也不解析 Agent 内部思维，也不把聊天当权威。

**这段话说明第一阶段如何验收：**  
用本地 OAuth fixture，两个人加三类 Agent，把正常路径、失败恢复、合同/语义冲突三条故事重复跑通。不连生产登录厂商。本机 `pnpm dev` 能起来，`pnpm check` 能过。
